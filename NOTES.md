# HaloModMenu — status and handoff

Last worked on 2026-10-13 (Reach reticle dot; see the end of this file). See README.md for how to build, install and use the mod. This file records where things stand and what is next.

## Where things stand

The mod targets Halo MCC Steam 1.3528.0.0. It's an in-game menu (open with LT + right-stick click or F6) that works across every MCC title. Halo 3, Halo: Reach, Halo: CE, Halo 2, ODST and Halo 4 have cheats; Halo 2: Anniversary multiplayer shows "not supported yet" and is out of scope (the mod is for campaigns only). You switch it on and off with `Desktop\Toggle-HaloModMenu.exe`, and anti-cheat must be off.

### Halo 3: ODST (ported 2026-10-02; full suite confirmed working the same day)

Everything on the menu works except equipment (greyed out then; ODST does have equipment, enabled 2026-10-11). Fixes found during the test (noclip invisibility, no overheat on a cooling weapon) went into Halo 3 too. `src/games/odst/` is a copy of `src/games/halo3/` (namespaces `OdstCheats`/`OdstTags`, class `Games::Odst`, macros `ODST_`), with every value re-found for `halo3odst.dll`. ODST runs Halo 3's engine but most layouts moved, so nothing was assumed equal without a check where one was possible. Tools in `tools/re/odst/` (`python mkimg.py` first):
- `port.py <h3 rva>`: finds the same code in ODST (masked byte patterns; a loose mode also masks displacements), `align2()` lines up whole functions, `map_global()` finds a global by mapping code that uses it.
- `hs.py`: ODST's script table (RVA 0x8184A0, 1,539 functions, found from a name string).
- `evdiff.py <name>`: a script evaluator side by side in both games; `evvote.py <disp>...` votes on how displacements map across all shared evaluators.
- `tagdiff.py`: tag field offsets from Assembly's Halo3MCC vs ODSTMCC plugins (`xml/`).

What moved (Halo 3 -> ODST): TLS slots objects 7->4, AI globals 6->7, game globals 9->8, player control 24->27, allegiance 48->47, directors 49->50, HUD 68->52; object health/shield/damage flags -0xC (0xE8/0xEC/0x104); unit actor/flags/team/player index -8 (0x160..0x170); unit seat/weapons/equipment/grenades/EMP +0x14 (0x262, 0x27C, 0x29C, 0x2A8, 0x392); weapon heat/age/barrels/triggers/magazines -8; equipment activation/uses -8; player control entries 0x2C0; skulls 0xFB10; AI grenades 0x3C4. Tags: vehi +0x20, weap +0x10, matg +0x10, bipd +0x28, scnr soft ceilings +0x34 and kill triggers +0x40, eqip uses +0x10. Unchanged: object header (position, vectors, parent, children, type byte 0x96), players slot and unit datum, game time, physics, allegiance friends, chud byte, director size, skull bit numbers (incl. Acrophobia 45), map/tag header formats. Code patches: AI can't fire is `41 0F 2F 4D 14` (5 bytes), recoil and third person have new patterns; AI blind/deaf patterns unchanged. Flip ejection: the unit update queues action 0x14 through 0x3C0E24 at 0x3894B2 (found statically, same shape as Halo 3).

No overheat fix (Halo 3 and ODST, 2026-10-02): turning it on while a weapon was still cooling from an overheat left it unable to fire until re-given. The weapon's overheated flag (word at Halo 3 +0x170 / ODST +0x168, bit 0x2; found live, a stuck beam rifle read 0x22) is only cleared by the game's cool-down, which zeroing heat skipped. Clearing the bit by hand freed the weapon; no overheat now clears it along with the heat (confirmed in ODST and Halo 3). Live-reading notes: heat is +0x180 in ODST (confirmed live). Assumed without a direct check (watch these in testing): player control yaw +0xD4 (pitch +0xD8 checked), director camera +0x8, "cannot die from damage" bit 0x10000, unit_add_weapon modes, and that the third-person branch means the same as Halo 3's.

### Halo 4 (ported 2026-10-02 while the user was away; full suite confirmed working the same day)

`src/games/halo4/` is a port of `src/games/reach/` (Halo 4 runs Reach's engine): same cheats and menu, every offset re-found for `halo4.dll` (namespaces `Halo4Cheats`/`Halo4Tags`, class `Games::Halo4`, title ID 3, macros `HALO4_`). Found statically with `tools/re/h4` and checked against the running game in Midnight (m90_sacrifice) where possible; `offsets.h` says which. Not available: fly (no Acrophobia skull) and no equipment despawn (armor abilities stay with you).

How it was found:
- **The script table is built at runtime.** Halo 4's HaloScript function definitions aren't in the DLL image; they're heap objects (vtable, return type, name, help, ..., evaluator at +0x60). `tools/re/h4/hsdump.py` scans the running game for them and writes `hs_funcs.txt` (name -> evaluator), which gave most engine functions, TLS slots and fields the same way as for the other titles.
- The user's Cheat Engine table has Halo 4 scripts; all their patterns match the Steam DLL uniquely. Used: rapid fire, no heat, third person (all NOPs), plus the field offsets their scripts touch (magazine, trigger, heat, battery, ability energy, jump).
- AlphaRing's offsets gave the main loop (0x616A8) and the per-tick world update (0x9A51C).

Checked live (memory reads/writes plus screenshots of the game): TLS slots by array name (players 1, objects 3, AI globals 6, game globals 8, squads 9, game time 18, player control 22, physics 68, actors 774), object header (tag datum +8, sibling/child/parent +0x1C/+0x20/+0x24, position +0x64, velocity +0x88), damage sections and the shield lookup (Chief: section 2), unit team/player/weapons/equipment/grenades, magazines (setting the reserve to 99 and grenades to 1 showed on the HUD), player control yaw/pitch (writing them turned the view and the unit followed), the HUD bit (clearing it hid the HUD), the third-person patch (Chief seen in third person; the director then runs the mode-0 following camera, which camera distance hooks), the tag system (instance table, group magics from the map's index header, matg/scnr pointers, tag names from the .map with mask 0 at header +0x4C4), and the tag fields the cheats use on the BR and Chief's biped.

Differences from Reach worth knowing:
- Give weapon: Halo 4 doesn't flag vehicle/turret guns "Cannot Be Used By Player", so the list also leaves out tags under `\vehicles\`, `\characters\`, `\equipment\`, `\turrets\` and `\unarmed\` (the carryable machine-gun turret stays).
- Aimbot: Halo 4 aims with each weapon's "Aim Assist Modes" block, so those fields are maxed too.
- AI can't hear: sets ai_set_deaf's flags on every actor (+0x35C bit 0x20) and every squad (+2 bit 1).
- Enemies can't see you: only the ai_disregard unit flag (Reach also had two perception NOPs; Halo 4's table has none).
- No recoil: firing damage cleared on the player's weapon tags (the table's recoil patch does the same thing from code).
- Cannot be ejected: Halo 3's shape, not Reach's. The unit update 0x62EA4C sends unit action 0x19 through 0x62C598 once the unit has been upside down longer than the seat's turnover time; the hook drops it for players when it returns to 0x62EB97.
- No HUD: clears bit 0 of the HUD mask (chud_show's bit) instead of 16 bytes.
- Rapid fire (first test 2026-10-02): the Cheat Engine patch made single-shot weapons (rocket launcher) fire every tick, but the SAW didn't speed up. Automatic weapons fire at their barrel's rounds per second (weap barrel +0x4, min/max; SAW 20, AR 10), not the per-shot recovery counter the patch removes. Rapid fire now also sets that to 60 (one a tick; the game runs 60 ticks a second) and fire recovery (+0x28) to 0 on the players' weapon tags, and on the vehicle's weapons with vehicle rapid fire. The SAW then sped up, but the AR still didn't: its fire recovery comes from Halo 4's title-update weapon tuning (a per-weapon-type table in the game variant, read by 0x61CB9C when the type has a rate-of-fire override) and the tag's values are ignored. Rapid fire now also turns the je at RVA 0x61CBCE into jmp, so every weapon uses its tag's (edited) values while it's on. Confirmed working 2026-10-02 (AR tag read 60/60 rps, 0 recovery, patch on): the muzzle flash speeds up, but the AR's firing sound keeps its normal pace (probably a looping sound); the user is fine with that. Raising the barrel's "Event Synchronized Projectiles Per Second" (+0x48, 8) was tried in a build and taken back out untested.
- Vehicle flags and checkpoints (all titles, 2026-10-02): a Halo 4 Wraith stayed invulnerable to rockets with the player outside it. It still had the mod's "cannot take damage" flag and AI reservation: a checkpoint saved while the player was in or boarding it brought the flags back on load, after the mod had let go of the vehicle, and `VehicleGodState` (memory.h) then took them for the game's own. It now remembers the last 32 vehicles it flagged and clears their flags whenever nobody's in them, so this is fixed for every title's vehicle god mode, Reach/Halo 4's no-EMP and AI reservation. Cleared on that Wraith by hand. Confirmed fixed 2026-10-02.
- Infinite grenades: the maxima are in the grenade globals tag (matg +0x6C8), 2 per type; 3 types (frag, plasma, pulse).

**First test (2026-10-02): everything on the menu confirmed working**, including rapid fire after the rounds-per-second fix, except two Vehicles-page issues, fixed and confirmed the same day:
- Vehicle god mode stopped the player punching open a Wraith's hatch while hijacking it (the player's parent is the target vehicle while boarding, so it got the flag). It now skips players sitting in a boarding seat, as no-hijack does.
- Cannot be hijacked: two allied Elites were seen riding on the sides of another Elite's Ghost. Clearing "Boarding Seat" (Reach's approach, a tag edit hitting every Ghost) turned the side boarding seats (seats 1-3, boarding index 0) into ordinary seats. Now the flag stays and the boarding seats' boarding seat index (+0x4A) is set to -1 instead, so they lead nowhere.

Original plan, before the test: the full menu, as for ODST. Most likely to need fixes: anything that calls the engine (noclip, give weapon's add mode 1, damage kills, checkpoints, aimbot pull), AI can't shoot / can't see / can't hear (no AI was nearby to check), camera distance, the Vehicles page (no vehicles in that part of Midnight; the Broadsword section later in the mission has the space fighter), and no overheat on a weapon that's already cooling (Halo 3/ODST needed an extra flag cleared; not looked for here).

## How it works (the non-obvious parts)

- **Menu Settings page (built 2026-10-02, needs a test):** `src/ui/menu_config.{h,cpp}` holds the menu's own settings (theme + accent/background/text/cheat-list colours, width, max height, font from C:\Windows\Fonts and size, open position, bindings, overlay toggles), saved in the `[Mod Menu]` section of the ini. Bindings are chords of up to 4 inputs: controller buttons (bits 0-15 = XINPUT_GAMEPAD_*, 16 LT, 17 RT; `Gamepad::HeldMask/PressedMask`) or keyboard keys (virtual-key codes; L/R Shift/Ctrl/Alt folded into the plain codes); a chord fires when all are held and one went down this frame. "Reset binding" captures the next N distinct inputs (menu navigation, back and close pause; 10 s timeout; then nothing fires until every input is released). Capturing a chord that ends on the select button (e.g. A + X) used to re-trigger "Reset binding"; menu navigation now pauses until everything is released (confirmed fixed 2026-10-02). Style and font changes are applied before the next NewFrame (`ApplyStyle`, `RebuildFont` + `ImGui_ImplDX11_InvalidateDeviceObjects`). Reset: main page = all of this game's settings, a category = its own options (`ResetPage`), Menu Settings = menu defaults. The Health/Shield readout was removed.

- **Saved settings (confirmed working 2026-10-02; per game since the same day, needs a test):** `src/ui/settings_file.cpp` keeps every toggle and slider in `HaloModMenu.ini` next to the DLL, a `[title]` section per game (name=value lines), loaded when the overlay hooks install and rewritten after any change (once a slider is let go). Each frame, before `Games::Tick`, the overlay asks `Games::RunningTitle()` and `SettingsFile::SwitchGame` stores the menu's settings as the previous game's and loads the new one's (a game with no section starts at defaults; the give/save/load button counters carry over so nothing re-fires). An old file without sections is copied to each of the five supported titles once. Outside a game the menu keeps the last game's settings. Give weapon and ammo type aren't saved: their tag IDs differ per map. A new setting needs a line in its `kEntries` table.

- **Menu pages:** `src/ui/overlay.cpp` has a `Page` enum and a `Draw...Page` function per category. To add a category, add it to `Page` and `kPageNames`, write its draw function and add a case in `DrawMenu`.

- **Loading:** the mod loads as `version.dll`, a proxy for the real DLL, from `mcc\binaries\win64`. It logs to `HaloModMenu.log` in the same folder, and the log can be opened while MCC is running.
- **MCC loads every title's DLL at once.** The running title comes from MCC's game-global object, not from load order.
- **Where engine functions can be called:**
  - Calling them from MCC's input polling (`get_key_state`) faults, because the per-thread index at Halo 3's TLS block +0x18 selects an empty table entry there.
  - Give weapon and the damage multiplier run from a hook on Halo 3's frame input update (`0xB414C`).
  - Noclip runs from input polling, because that timing felt right. During its teleport it borrows the frame's thread index so the teleport finishes. It pauses while the player is seated, because teleport detaches seated objects.

### Lock checkpoints and checkpoint history (Reach, Game State page, built 2026-10-08, needs a test)

MinHook on the per-object update `object_update(datum)` (RVA 0x8D7630; the tick's loops 0x8DD7F0/0x8DD920 call it for objects whose table entry byte +2 has bit 4 "needs update", and it recurses into children itself, which goes through the hook too). `Tick` rebuilds, every game tick, a table of frozen datums (by table index): every AI unit (biped or vehicle with an actor, not a player) and everything attached to it (held weapons, equipment, seated units), and each vehicle it rides (up to 4 levels) unless a player is in it. The hook returns early for those: no animation, physics, weapon or melee update. Switching off clears the table at once. Released objects should simply update again: a skipped object keeps its "needs update" bit 4 (cleared only by 0x8DBE70 at the end of a real update), so it is called again every tick. This differs from Reach (whose skipped objects got a stuck flag); this is only read from the code, if AI stay stuck after release, check the entry byte +2 and obj +0xC0 flags of a frozen unit. The actors themselves keep thinking (not deactivated, unlike Reach's actor_set_active(false) which was found not enough on its own); not tested whether that makes them act in a burst after release. Projectiles already in flight keep moving; a barrel already marked to fire may still produce one shot (0x8EF960 runs after the update loops). Vehicles may still coast if their physics runs outside the object update (not checked).


#### h2_fun

### Halo 2 launch on hit, giant/tiny AI, double/infinite jump, poison touch (Halo 2, built 2026-10-10, needs a test)

All in `src/games/halo2/fun_extras.cpp` (`Halo2Fun::Tick`, once per game tick, each feature in its own SEH block); offsets in `fun_extras_offsets.h`. Tuning constants at the top of the .cpp. Syntax-checked only (cl /Zs), nothing run in game.

- **Launch on hit.** Same as Reach/CE: every enemy AI biped (first sight: `IsKillableEnemy`; after that followed to its death, because a dead unit loses its actor) has its own health/shield table (`+0xEC/+0xF0`); a drop since last tick, or health <= 0, adds `launchStrength` to its upward velocity (read `+0x88`, add, `object_set_velocity` core 0x8DB9D0, linear only). Seated units skipped. Why this should stick: the engine's own biped jump (0x928AD0) computes `vel += (jump - dot(vel, up)) * up` and applies it with the same 0x8DB9D0 call, on grounded bipeds, AI included. Gravity (`*(float*)*(OFFSET_HALO2_GRAVITY)`, read live) is 4.17, same as Reach; the player's jump velocity in the tag is 3.08 (world units per second, so object velocity is per second, not per tick like CE). Default 12 therefore is about 4 jumps high. Unverified: whether ground adhesion pulls a standing biped back before it leaves the floor (12 u/s should beat it), and corpses (ragdoll, physics mode 3) get launched too.
- **Giant / tiny AI.** `object_set_scale` core **0x90A410** (evaluator 0x783F20, found with `deep.py object_set_scale`): `(object datum, float scale (xmm1), uint16 ticks (r8w))`, ticks 0 = instant. It recurses over the child list (first child +0x10, next sibling +0xC), so held weapons are scaled by the one call (no per-weapon loop like CE). It stores the scale at object **+0xA0** (0x8DB5E0), then fixes up bounds. Verified live: +0xA0 reads 1.000 on every object in the table (Regret). The call itself is untested. Per tick every AI biped (actor != -1, not a player, not seated, alive) whose scale differs from its side's slider gets the call; units it changed are put back to 1.0 when both sliders return to 1 (units the game scaled itself are left alone). Friendly = team player/human, or player 1's team (Arbiter missions: Covenant). Risks: giant AI stuck in doors / clipping; weapons picked up after scaling are not rescaled until the unit's own scale changes.
- **Double / infinite jump.** The biped jump function is 0x928AD0 (reads the tag's jump velocity at bipd +0x1F8 into xmm6, applies via 0x8DB9D0). Grounded/airborne test: biped word **+0x390 bit 0x1000**: the post-physics update (0x929300-0x929A30) clears it every tick and sets it again, copying the ground point/normal to +0x3B0/+0x3BC, when the character physics found a ground surface (fall damage reads it too). Live: set on every living biped on the floor, clear on corpses; that it clears in mid-air is read from code, NOT seen live (nobody jumped during the sampling). Also required: physics mode byte **+0x428 == 1** (ground mode; 3 = dead, live), not seated (parent -1), health > 0, `!s.noclip` (noclip pins the unit anyway). A press (FrameInput::jumpPresses changed) after >= 4 airborne game ticks (so the take-off press isn't spent) and fewer than `airJumps` air jumps this trip (or infinite) sets vertical velocity to the tag's jump velocity (read live from the tag, so the Jump slider applies) keeping horizontal, with the 0x8DB9D0 call. No jump animation is triggered (the engine's own jump calls 0x928DC0/0x926C50 for that; not called). Note: bit 0 of +0x390 is NOT "on ground": it is the jump-held input bit (counted into +0x3E1); the ground test is 0x1000.
- **Poison touch.** Any AI biped (actor != -1, not a player, health > 0) within 1.0 horizontally / 1.5 vertically of player 1 (its own position, so a seated unit only counts when its seat is that close): clear `HALO2_DAMAGE_FLAG_CANNOT_TAKE_DAMAGE` (0x80) in +0x10A, shield and health set to 0, then `unit_kill`'s core **0x8FAF30(object datum)** (evaluator 0x784FE0; it ors 0x20 into +0x10A and wakes the object, the same flag write the damage multiplier does by hand, which is live-tested). The core call itself is untested. Only bipeds (AI-driven vehicles are not killed, only their riders when close).
- Not done / not wired: nothing needs wiring (Load/Unload/Reset/Tick already called). Time stop is not consulted (frozen units still get launched/scaled). No feature-bit changes needed (kLaunchOnHit, kPoisonTouch advertised; kAiScale and kDoubleJump bits are Features2: check halo2.cpp advertises them).

### Upgrade AI, Random AI swap and Squads (Halo 2, built 2026-10-10, needs a test)

**How replacing works** (`ReplaceActor`, shared by Upgrade AI and Random swap; Reach's/CE's recipe): read the old AI's position (+0.25 up), facing (object forward, +0x70), team (unit +0x13C) and squad (actor +0x30). Make a fresh squadless actor with `Halo2Internal::SpawnActor(character, ..., team 0)` (own team, picked loadout), move it into the old one's squad with the per-actor core of `ai_migrate`, set the old team again, then erase the old one with the per-actor core of `ai_erase` (actor delete, then object_delete of its unit). New before old, so a mission squad is never empty and scripts counting the squad keep working. Failure to spawn leaves the old AI untouched.

**Halo 2 engine facts** (HS table, tools/re/h2):
- Halo 2 has squads, no encounters. Squads are the 0x98-byte records at `OFFSET_HALO2_AI_RECORDS` (the array `ai_set_deaf` already used); an actor's squad index is actor +0x30 (-1 = squadless). Checked live on 05b_deltatowers: a marine had +0x30 = 0 and squad 0's +0x68 (first actor) held its datum; two buggers had 4 and 3 and squads 4/3 pointed back at them. Actor +0x54 is the 'char' tag datum (marine, bugger, bugger, live).
- `ai_migrate` (evaluator 0x786780) -> 0x619E40 -> 0x619C50 walks a squad's actors and calls **0x625840(actor datum, int16 squad index)** for each: detaches from the old squad (0x63A5A0), attaches to the new one (0x63A380(actor, squad, 1)) if the actor is awake (it is: SpawnActor sets it active), else stores the squad in actor +0x34 for later. Static only.
- `ai_erase` (evaluator 0x786560) -> 0x618CC0 per actor: reads the unit (+0x18), calls **0x624B20(actor datum)** (ends in a tail call to 0x623490(actor, 1) = the real actor delete; the unit death path 0x8F6BAF calls it too), then object_delete(unit). Mirrored exactly. Static only; ai_erase also defers the actor that is currently running its update (a global read at RVA 0x618D05); the mod runs before the tick, so that case can't arise.
- Object forward vector at +0x70 (live: unit length, horizontal, matched the facing).

## Laser sight dropped (2026-10-13)
The laser idea was scrapped entirely at the user's request ("one game out of six and it's a mess"): the overlay beam, the Reach world dot (effect call 0x117634, effect picking, collision flags 0x100000809), the settings (`laser`, `laserColor`), `Feature2::kLaser`, the Weapons page Sight section and the TODO lines are all removed. The earlier sections of this file that describe the laser/dot are history only. If it's ever revisited: stock effects are the limit (no tintable dot; the red flare exists in few maps, the firefly swarm is slow and spread out), and the collision flags that stop at AI in Reach were 0x100000809 / 0x100024809 (bit 32 = bipeds).
Reach double jump fix (2026-10-13, built, needs a test): the log showed presses made at the top of a normal jump (feet 0.67 above the ground, jump height 1.0x) all counted as grounded because the downward ray (`kAirGap`) was 0.9 world units: a normal jump never got that high, so air jumps only worked from ledges or with a raised jump height. `kAirGap` is now 0.25. Halo 4's `kAirGap` is still 0.9 (halo4/fun_extras.cpp) and may have the same problem at normal jump height; CE, Halo 2, Halo 3 and ODST were not checked. The 12-line "jump press" debug log stays until it's confirmed.
Double jump gap, all titles (2026-10-13): Reach's fix (0.9 to 0.25) confirmed. Only Halo 4 also decides "airborne" with a downward ray, so its `kAirGap` is now 0.25 too (built, needs a test). CE, Halo 2, Halo 3 and ODST use the game's own airborne/ground flags, so they have no gap to fix.

## Banshee exit crash (2026-10-13)
Taking a Banshee with the pilot-seat key, then leaving it crashed MCC right after "detaching player 1 (taken pilot seat)": the Banshee has a normal exit that was already running, and our objects_detach hit mid-exit. The quick 0.4 s hull-exit detach now applies only to AI-only vehicles (Pelican/Phantom); everything else, taken or not, waits the 1 s stuck-seat hold. Built, untested.
Phantom exit crash with "Cannot be ejected" on (2026-10-13): the objects_detach makes the game send the flip-eviction eject action, our hook dropped it, and MCC crashed (with the option off it worked). ExitHull now calls AllowEject(player unit) just before the detach and clears it when the exit finishes or times out (and on map change). Built, untested.
